# EditAnt: seed of the spec (PM draft of 2026-11-19, for the lane to expand and CireSnave to mark up)

Markers: **[said]** CireSnave, **[PM]** the PM's proposal. Nothing here is verified against prior art: that survey is the lane's first job.

## 1. What CireSnave said (2026-11-19, verbatim)
> "My initial thought is that the project would be editing Markdown files since that is what both human developers and LLMs use most often. Markdown has sections with headers. My thinking is that the tool could enable an LLM to replace specific sections of the document by name (the name being their header text). We would likely add more to the tool later but that alone would allow you to go back and edit a previously created section of a document without worry of corrupting or erasing anything beyond that section. The tool would show the original section being replaced (or removed) followed by what it would be replaced with, if anything, and the LLM would approve or deny their own edit."

Earlier idea (2026-11-01): a hierarchical-file editing tool for Markdown, TOML and JSON, addressed by section. Not started.

## 2. MVP [PM amendments to the above, for CireSnave to accept or change]
1. **Outline and read first.** To address a section by name the caller must see the names: `outline(file)` and `read_section(file, path)` are part of the MVP (read-only, tiny).
2. **Address by header path, not bare text.** Header text is not unique. A section is addressed by its path (`Parent > Child`) with an optional occurrence index; an ambiguous or missing address is REFUSED, never guessed. The parser is CommonMark-aware: ATX and setext headers; `#` lines inside fenced code blocks and front matter are not headers; the text before the first header is the preamble section.
3. **A section's extent.** Default: the section's own body only, from its header line up to the next header of ANY level, so a replacement can never touch a child section. Replacing a whole subtree is an explicit flag, and the preview then says how many child sections it covers.
4. **Preview, then apply, bound by a token.** `preview(file, path, replacement|none)` writes nothing and returns the original section, the replacement and a diff, plus a token binding {file, path, hash of the original section, hash of the replacement}. `apply(token)` fails if the file changed since the preview (stale-edit protection). The LLM's own approve/deny is kept, but the real safety is the bounded scope plus the token; a human-approval mode is an option for later.
5. **Everything else byte-for-byte.** No reformatting of untouched text; line endings (LF or CRLF), final newline and encoding preserved; replacing a section with itself returns identical bytes (a property test, with sabotage checks).
6. **Delete is replacement with nothing.** Insert-after and insert-before a named section come next, then rename of a header.
7. **Not in the MVP:** other formats (TOML, JSON: later, behind a format-agnostic tree-of-addressable-nodes interface), a GUI, merging, history.

## 3. Shape and place [PM]
- A library crate plus a CLI first; the MCP server is a thin second layer (the MCPAnt project is a reserved name only today). The layering CireSnave set on 2026-11-18: field libraries, then AnalysAnt lenses, then MCP tools, then editing tools: this is the editing-tool layer.
- Deterministic; no model inside; `#![forbid(unsafe_code)]`; permissive dependencies only; reuse a good existing Markdown parser (for example `pulldown-cmark`, MIT) after the survey, keeping its licence and credit.
- Every claim in a README or doc is earned: built and tested.

## 4. Before any code (the lane's first job)
1. Survey what exists (Markdown parsers with source offsets, existing section-editing tools and MCP servers for documents); list what was read and what was only seen.
2. Write `docs/SPEC-STEP1.md`: scope, non-goals, API sketches, what is unverified, and every decision that needs CireSnave as an `[ASK]`.
3. ONE PR with it. No code until CireSnave has read the spec.
